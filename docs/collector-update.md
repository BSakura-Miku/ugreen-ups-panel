# 通过面板更新采集器

v0.9.0 在「诊断与说明」加入采集器更新。首次启用需在 NAS 安装独立的宿主更新服务，并给面板挂载它的本地通信目录。之后可在页面检查正式发行、查看说明、更新采集器和回退兼容版本。

它只处理本项目采集器代码。面板 Docker 镜像、宿主更新服务自身、NUT、UPS 固件和 NAS 系统仍分别维护。没有定时检查或自动安装；打开页面、刷新状态均不访问发行服务器。

请使用 v0.9.1 或更新版本的安装脚本；v0.9.0 的更新服务在部分 systemd 环境中会因通信目录的属组被重置而启动失败。安装失败会撤销更新服务安装，原采集器继续运行。

**已启用网页更新的用户直接按[日常操作](#日常操作)更新**，无需每次重新执行首次安装命令。面板、采集器和宿主更新服务分别维护，版本号不必相同：2026-09-09 实机使用面板 v0.12.0、更新服务 v0.9.1，完成了采集器 v0.9.1 → v0.12.0 的网页升级，更新服务仍为 v0.9.1。具体兼容要求以目标版本说明为准。

v0.12.1 新增的源码与配置预检由宿主更新服务执行。要启用这些保护，需要先按[更新宿主更新服务](#更新宿主更新服务)更新它自身；只在网页安装新版采集器不会替换更新服务或其中的安装器。旧服务继续兼容，但页面不会把它未提供的预检显示为已通过。

## 首次启用

先按 [README](../README.md)安装并确认已有采集器正常工作。v0.8.0 采集器可直接作为网页更新的起点。备份原数据库与校准配置，见[备份说明](architecture.md#备份与维护)。

在 **NAS 宿主机**执行以下命令。将路径改成原部署目录；自定义过 Compose 项目名时，为所有 Compose 命令加上同一个 `-p 原项目名`。保留已有 `docker-compose.yaml` 和 `data/`。

```sh
(
  set -eu
  ups_project_dir=/volume1/docker/ugreen-ups-panel
  ups_update_tmp="$(mktemp -d)"
  trap 'rm -rf "$ups_update_tmp"' EXIT
  curl -fL https://codeload.github.com/BSakura-Miku/ugreen-ups-panel/tar.gz/refs/tags/v0.12.1 -o "$ups_update_tmp/source.tar.gz"
  tar -xzf "$ups_update_tmp/source.tar.gz" --strip-components=1 -C "$ups_update_tmp"
  sudo sh "$ups_update_tmp/scripts/install-updater.sh"
  # 首次创建可选覆盖文件；如已存在，先检查其内容，不覆盖个人设置。
  if [ ! -e "$ups_project_dir/compose.updater.yaml" ]; then
    sudo cp "$ups_update_tmp/compose.updater.yaml" "$ups_project_dir/compose.updater.yaml"
  fi
  sudo docker compose -f "$ups_project_dir/docker-compose.yaml" -f "$ups_project_dir/compose.updater.yaml" pull
  sudo docker compose -f "$ups_project_dir/docker-compose.yaml" -f "$ups_project_dir/compose.updater.yaml" up -d
)
```

覆盖文件只添加 `/run/ugreen-ups-updater` 的只读目录挂载；目录必须由已安装服务准备，Compose 不自动创建它。默认容器用户 root 和 `10001:10001` 均可连接。使用其他容器 UID 时，需要给容器补充 GID `10001`。后续重建面板时也保留这个覆盖文件；通过 NAS Docker 界面管理时，将其中挂载合入原项目配置即可。

首次启用还会移除现有项目源码的组写与其他用户写权限，保留代码内容与所有者；已有服务、环境文件和数据目录不因此改动。安装失败会恢复此前的源码权限。

首次安装自动生成管理密钥，重装保留原密钥。在 NAS 终端读取：

```sh
sudo cat /etc/ugreen-ups-updater/key
```

将密钥填入「检查与管理更新」展开后的「管理密钥」。它只留在当前页面内存中；收起管理、离开诊断页或刷新后需重新输入，也可主动清除。查看版本和进度不需要密钥，检查新版、安装及回退需要密钥。面板不会读取宿主密钥文件，也不会将密钥写入浏览器存储、操作记录或诊断导出。

密钥赋予采集器更新权限，应作为密码保管。面板普通遥测和校准仍没有登录机制，继续只在可信网络使用；需要跨网络管理时，通过自己的 HTTPS 入口访问，避免明文传送密钥。不要将密钥放进 URL、截图、公开问题或访问日志。

## 更新宿主更新服务

在 NAS 上下载并展开包含所需修复的正式发行源码，进入该源码目录后执行：

```sh
sudo sh scripts/install-updater.sh
```

这是更新服务自身的命令行升级，使用发行源码中的新服务与安装器，保留已有管理密钥和操作记录。已有通信目录挂载继续使用，不需要重建 Compose 项目；安装完成后在更新卡片核对「宿主更新服务」版本。该命令不更新采集器，也不修复采集器环境文件中的错误路径。

如果此前采集器未接入校准文件，另按 [README 的采集器命令行更新步骤](../README.md#更新)，让 `--data-dir` 指向现有面板 `/data` 挂载对应的宿主目录。确认原数据库和校准文件位置后再执行，不以新建空数据目录代替修复。采集器恢复后再使用网页更新。

旧更新服务缺少预检字段时，界面明确显示「尚未提供完整配置预检」。旧采集器没有校准目标身份时只能核对配置内容，路径仍是尚未核实；不能把两边内容相同当作已证实使用同一文件。

## 日常操作

1. 打开「诊断与说明」，确认当前实时采集正常、更新服务可用，查看源码和配置预检说明。在「采集器更新」卡片点击「检查与管理更新」，输入管理密钥。
2. 点击「检查更新」。等待「稳定发行版检查已完成」，核对「最新稳定版」和本次检查时间。这里只查询发行版，尚未安装。
3. 有可安装版本时，点击「查看并更新」，核对目标版本与当前版本；可展开「安装包校验信息」查看 SHA-256。
4. 点击「确认安装此版本」才会开始下载和安装。页面显示下载、校验、安装及采集验证阶段；较快的阶段可能在相邻两次状态刷新之间完成，不显示估算百分比。
5. 等待「采集器已更新，遥测恢复检查已通过」，确认该记录的原版本、目标版本及时间属于本次操作，再按下方方法验收。更新会短暂重启本项目采集器，历史中可能出现短连接间隔；原历史与校准配置保留，NUT 保护服务保持运行。

「最新稳定版」展示上次主动检查的结果。重新打开或刷新页面不会检查 GitHub；如果仍显示旧版本，先点击「检查更新」并核对检查时间。看到新版或「稳定发行版检查已完成」，都不代表已经升级。

页面关闭或刷新不会取消已接受的操作。重新打开可恢复进度；更新服务正常停止时会等待正在执行的操作结束。一次只允许一个操作，手动命令与网页更新共用安装锁；提交时检查版本和源码指纹，避免下载期间发生手动升级后覆盖新版本。

检查结果在当前更新服务进程中最多用于安装一小时。服务重启或信息变化后需重新检查。下载时再次核对发行附件身份及 SHA-256；网络或校验失败不会切换采集器代码。

### 源码与配置预检

新版更新服务分别检查已安装源码、实际运行采集器和校准文件。发现明确问题时，界面暂停安装与回退，仍可查询发行版。修复后重新读取状态，再选择更新目标。

| 结果 | 处理方向 |
| --- | --- |
| 源码与发行指纹不符 | 先核对并保留本地补丁，通过命令行恢复正式源码；补丁不会自动合并 |
| 实际运行与已安装源码不一致 | 核对服务的源码目录、旧进程和重复采集器；该结果本身不等于发现源码修改 |
| 校准路径未接入、文件不可读 | 使用现有数据目录重新运行采集器安装器，检查权限、环境文件及 systemd 覆盖项 |
| 校准配置不兼容 | 核对配置名、格式和系数；12 V 使用官方 `custom` 与 12 V 档位 |
| 文件与采集器配置不一致或目标未验证 | 检查实际配置路径，等待新样本；若缺少新功能则先更新对应宿主组件 |
| 面板与采集器指向不同校准文件 | 修复面板 `/data` 挂载与采集器配置路径；两边内容相同也不能代替同一目标 |
| 更新期间配置变化 | 等待采集器确认新配置后，重新检查并选择目标版本 |

没有发行指纹的旧安装会明确标为无法核验来源，不能显示为源码检查已通过。安装器在切换后继续核对新鲜遥测、运行代码身份和配置读取；仅有心跳或磁盘版本号改变不足以完成验收。

## 升级后核对

1. 在「版本信息」确认「采集器」已显示目标版本，实时数据时间继续更新。更新卡片在成功记录下分别显示「实时采集」「校准配置」「历史写入」的当前检查结果；连接检查中的快照与私有报文也应恢复。UPS 固件等设备未提供的字段仍可能显示「未知」，不作为升级失败的依据。
2. 清除管理密钥或收起管理后刷新页面，再确认版本和本次成功记录仍在。需要了解恢复选项时，可重新展开管理，查看「回退到上一版本」中的目标；查看回退目标不会执行回退。
3. 回到「电力概览」，确认历史趋势继续产生新记录；已配置有效交流估算时，用电统计继续累计。已有记录应保留，短暂重启产生的缺采不补算。

采集器和更新服务的版本来源分别显示：

| 页面位置 | 信息来源 | 核对用途 |
| --- | --- | --- |
| 「版本信息」中的「采集器」 | 面板所读采集快照中的构建信息 | 配合持续更新的实时数据，确认正在上报的采集器版本 |
| 「采集器更新」中的「已安装采集器源码」 | 宿主安装目录中的代码 | 确认安装目标；读取不到时显示未知，不用运行快照填充 |
| 「采集器更新」中的「实际运行版本」或「最近报告版本」 | 采集器发布的构建信息及诊断新鲜度 | 区分当前有效运行报告与旧报告，核对是否与安装目录一致 |
| 「采集器更新」中的「宿主更新服务」 | 当前提供更新接口的宿主服务 | 判断更新服务自身是否已升级，不能用采集器版本代替 |

安装成功记录与当前运行检查分别保留。已有数据库权限或锁冲突不会被改写成采集器安装失败；历史项会显示具体原因。诊断连接中断或数据过期时，当前检查显示等待或未知，不沿用旧的全部通过结果。

「构建详情」中的提交号可能未随快照提供；需要进一步核对时，可比较版本与源码指纹，不因提交号缺失单独判定升级失败。

## 升级后信息异常

如果已经升级，但「已安装采集器源码」显示新版，而「版本信息」中的采集器版本或「连接检查」中的宿主采集条件等仍为「未知」，先保留现场信息。正常新版采集器会随实时数据上报这些信息；需要核对实际运行的服务、是否有重复采集进程，以及面板的快照挂载与 `UPS_SNAPSHOT` 配置，不能仅凭版本卡片判断是哪一种原因。

供进一步排查的材料：

- 在「下载诊断记录」点击「下载 JSON」，并记录本次更新结果、目标版本和时间。诊断下载不包含更新操作日志，必要时另附更新卡片截图。
- 提供实际使用的 Compose 配置，核对采集快照和 `/data` 挂载；分享前移除密钥、设备标识及个人地址。
- 如果同时提示「历史记录暂不可用」，提供面板容器日志中 `History writer:` 后面的具体错误。采集器信息缺失与历史写入失败需分别排查；目录权限、数据库锁或数据异常应根据日志确认，不以删除数据库或重装代替定位。
- 如果问题是校准保存不可用或 `/api/calibration` 的 `collector_ready: false`，核对采集器是否通过 `UPS_CALIBRATION_CONFIG` 读取了面板实际保存的同一文件，见[校准配置路径核对](calibration.md#校准保存不可用时)。该状态与采集器版本字段是不同检查。

宿主服务状态和日志命令见下一节；只读自检及诊断下载范围见[诊断说明](diagnostics.md)。

## 回退与异常

更新包安装到独立版本目录。安装器保留先前代码与服务状态，切换后等待新的 USB 样本及心跳；验证失败会尝试恢复先前版本。页面区分「已恢复原版本」和「需要检查服务」，不会把失败恢复也显示成成功。

网页回退只用于通过保留配置模式产生的兼容备份，最早支持 v0.8.0。旧安装器产生的备份可能同时恢复宿主配置，因此不提供网页回退按钮；需要时按原版本的命令行回滚说明处理。回退不删除其他版本目录，也不回退历史数据库或面板镜像。

NAS 断电或强制终止进程可能中断事务。服务重新启动会显示上次操作被中断，并重新读取当前版本；不会根据旧记录自动再装一次。若采集未恢复，在 NAS 检查：

```sh
sudo systemctl status ugreen-ups-updater.service ugreen-ups-collector.service --no-pager
sudo journalctl -u ugreen-ups-updater.service -u ugreen-ups-collector.service -n 60 --no-pager
```

未安装、通信目录未挂载、目录权限不匹配和服务停止都会使更新卡片不可用，不影响已有遥测与历史接口。发行服务器访问失败时检查 NAS 网络；更新服务使用宿主进程的无凭据 HTTP(S) 代理环境，不沿用浏览器代理。

## 权限与发行包

宿主服务只监听 Unix socket，没有 TCP 监听端口。通信目录权限为 `0750 root:10001`，socket 为 `0660 root:10001`；管理密钥单独保存在宿主 `0600` 文件中。所有写操作还需密钥校验，HTTP 接口检查同源、自定义请求头、请求大小和固定字段。更新服务不接受任意命令、路径、仓库或下载 URL。

下载来源固定为 `BSakura-Miku/ugreen-ups-panel` 的正式 GitHub Release。版本包名为 `collector-v版本.tar.gz`，使用 GitHub API 提供的 SHA-256，缺失时读取同发行的 `SHA256SUMS`。HTTPS 和固定仓库定义来源信任；SHA-256用于完整性检查，不等同于独立维护者签名。

包最多 4 MiB，仅包含 `ups_panel/*.py`、固定版本元数据和 `LICENSE`。拒绝路径穿越、绝对路径、重复成员、链接、特殊文件、扩展归档头、大小超限及不兼容版本。安装前重算源码指纹并核对版本，解析时不导入下载代码。执行的是首次安装在宿主的固定安装器；下载包没有可执行安装脚本或服务配置。正式发行中的采集器 Python 代码仍是受信任代码，安装后由原采集器服务运行。

常规网页更新保留现有 systemd 配置、采集器环境文件、数据目录权限、校准和历史，仅切换采集器代码与重启本项目服务。安装器、预检和宿主更新服务代码的修复需要执行上方的命令行升级；网页更新包不包含它们。

源码中的本地修改不会自动合并到正式发行包。若自行新增了校准配置名或修改模型，后续安装正式版本可能使保留的配置不再被识别；升级前应核对并迁移到正式支持的配置格式。保留配置文件不等于保留对定制配置的代码支持。

标准 Docker 部署中，用 `docker cp` 写入现有容器 `/app/ups_panel/` 的补丁会在该容器重启后保留，但删除、重建或用新镜像替换容器后不保留。`/data/calibration.json` 的持久化与容器源码补丁是两回事，升级前应同时核对两者的兼容性。

## 停用

在对应版本的源码目录执行：

```sh
sudo sh scripts/uninstall-updater.sh
```

这会停止并禁用更新服务，移除其 unit 与 socket；采集器继续工作。更新服务代码、管理密钥和操作记录保留，便于重装。删除 Compose 中的可选更新挂载并重建面板即可停用面板中的采集器更新操作；卡片会显示未安装或不可用。不要删除原采集快照挂载或 `data/`。
