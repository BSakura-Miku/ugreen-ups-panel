# 历史存储与一年规模性能

一年历史使用日聚合保存。正常保留窗口下，一年查询读取的行数远少于 90 天查询；本次合成测试中，NAS 的一年查询约为几十毫秒，90 天查询约为 2 秒。这里的时间仅指数据库查询与 Python 聚合，不包含 HTTP、网络传输和浏览器绘图。

## 保留内容与规模

| 数据 | 保留范围 | 保存内容 |
| --- | --- | --- |
| 10 秒聚合 | 最近 7 天 | 各指标总和、有效计数、最小值、最大值与来源上下文 |
| 60 秒聚合 | 最近 90 天 | 同上；同时作为日聚合的增量来源 |
| UTC 日聚合 | 最近 365 天 | 保留与窗口相交的最早一天，可能包含部分边界日 |
| 状态事件 | 最近 180 天 | 连接及供电状态变化 |
| 电池供电明细与能量 | 最近 365 天的相关记录 | 观测起止、完整性与能量依据；进行中记录单独保留 |

后端通常每 2 秒检查一次快照，约每 10 秒提交一次聚合；相同采样时间不会重复累计。它不无限保存逐 2 秒采样或逐帧 USB 数据。历史查询可比实时数据晚一个提交周期，缺失、过期或尚未采集的时段不会自动补齐。

在每个桶只有一个供电模式、一个校准上下文的简化情况下，包含当前桶时，三层约为 **60,481 + 129,601 + 366 = 190,448 行**。这不是全局行数或磁盘占用上限：主键还包含 `mode` 和 `context`，同桶的供电模式、校准系数、质量状态或版本改变会增加记录。清理约每小时运行一次，其间也会暂存稍早的桶。

各指标按自己的有效计数计算加权均值。不同模式、公式或校准上下文保持分组；调整校准不会重算过去的记录。日统计与回填游标在同一事务中提交，重启不会把已处理的分钟记录再次累计。旧库只能从仍存在的分钟数据补建日统计，不能恢复已经删除的历史。时间边界与 CSV 字段见[架构文档](architecture.md#分层历史)。

## 为什么 90 天比一年更重

查询 24 小时以内时读取 10 秒桶，超过 24 小时且不超过 90 天时读取分钟桶，超过 90 天时读取日桶。因此连续 90 天需要处理约 129,600 个分钟桶，而一年通常只需数百至数千个日／模式／上下文分组。

SQL 使用现有 `(resolution, bucket, mode, context)` 主键索引按粒度和时间范围定位；本次执行计划没有扫描整个 `samples` 表。排序仍需处理同一桶内的 `first` 顺序。主要开销是读取、解析和合并所选桶中的 JSON，不是重新读取一年内的全部原始采样。

返回数据以约 1,200 个时间分组为目标再合并，仍保持模式和校准上下文分组，因此 1,200 不是返回点数硬上限。本次 90 天返回 1,442 点，紧凑 JSON 为 3,083,260 字节；一年返回 1,096 点、2,347,645 字节。HTTP 编码、传输和绘图仍有额外成本，长范围自动刷新应降低频率，并避免同一页面叠加未完成的请求。

此次查询改动用 SQLite 游标逐行合并，仅在建立新输出分组时解析上下文。它移除了 `fetchall()` 的整批行列表，不改表结构、保留周期、指标加权方式、校准分组或写入路径。全部六个历史范围、事件和五个供电明细范围的新旧响应序列化后逐字节一致。

## 2026-09-07 合成测试

数据集按实际 schema 2 构造，固定窗口终点为 2026-09-07 12:00:00 UTC：17 个数值指标、四种季度校准上下文、每日 15 分钟电池供电及 60 分钟回充。保留 60,480 个十秒桶、129,600 个分钟桶和 1,096 个日／模式桶，另有 8,640 个事件、365 条供电明细及其能量记录。日层代表 15,768,000 次合成的 2 秒观察，各层存在重叠，不能相加当成独立观察次数。

数据库为 **524,046,336 字节，约 500 MiB**，包含表和索引。这是上述完整指标与上下文的合成样本，不是每台设备一年必然占用的大小。实际字段是否有效、模式和校准变更频率、SQLite 页利用率、WAL 与数据库曾达到的大小都会影响磁盘占用。删除过期记录通常让数据库内部页面可复用，不保证主文件立刻变小。

基线为提交 `750717efe904586ddeeaea57744e81fab5448a37`；对照仅替换流式查询的 `storage.py`，文件 SHA256 为 `eb8bd48a3226268f90db5ed22f2ee80b663a2554f99b74c538f9933a8d11d975`。两组源码被冻结后测试，使用同一个合成库。

### 本机重复查询

环境为 Apple M4、16 GiB 内存、macOS arm64、Python 3.12.14、SQLite 3.53.4。每项在独立进程内连续测量 5 次；p50 是中位数，p95 是这 5 个样本的插值，不能代表长期尾延迟。未清空系统缓存，接近热缓存测试。RSS 是该进程完成查询和紧凑 JSON 编码阶段的内存高水位，包含解释器与多次测量的分配开销；计时列不包含编码。

| 范围 | p50 毫秒：基线 → 流式 | p95 毫秒：基线 → 流式 | RSS MiB：基线 → 流式 |
| --- | ---: | ---: | ---: |
| 1 小时 | 6.78 → 5.55 | 7.33 → 6.27 | 34.09 → 33.89 |
| 24 小时 | 105.05 → 91.43 | 107.08 → 92.49 | 74.22 → 59.41 |
| 7 天 | 119.49 → 104.66 | 127.22 → 119.17 | 69.81 → 52.45 |
| 30 天 | 494.10 → 430.70 | 508.85 → 446.44 | 134.00 → 54.97 |
| 90 天 | 1,529.48 → 1,260.17 | 1,574.89 → 1,316.07 | 292.92 → 58.09 |
| 365 天 | 17.46 → 18.11 | 18.16 → 19.44 | 62.25 → 61.45 |

随后在同一进程额外查询一次，用 `tracemalloc` 测量当次 Python 分配峰值，90 天从 221.92 MiB 降至 10.49 MiB；该次查询不参与前述耗时和 RSS 统计。它与 RSS 统计对象不同，不能相互替代。

事件查询返回最近 100 条，p50 为 0.37–0.41 毫秒。一年 365 条供电明细的查询 p50 约 3 毫秒。额外构造每日 12 次、全年 4,380 条供电片段的压力样本时，一年明细 p50 为 37.63 毫秒、Python 分配峰值约 24.69 MiB。明细查询为生成范围汇总会处理范围内全部记录，`limit=50` 只限制返回明细条数；它也不是任意记录数量下的固定成本查询。

### NAS 单次只读比较

在 Linux x86_64 NAS、Python 3.11.2、SQLite 3.40.1 上，将同一合成库放在任务独立临时目录中。每个版本、每个范围仅运行一次，数据库以 `mode=ro&immutable=1` 和 `query_only=ON` 打开，跳过初始化、迁移、写入与并发压力。每次先执行 `quick_check`，所以查询前已有缓存预热。

| 范围 | 基线查询 | 流式查询 | 含 JSON 编码的进程峰值 RSS：基线 → 流式 |
| --- | ---: | ---: | ---: |
| 90 天 | 2,494.63 ms | 2,020.68 ms | 256.37 → 41.47 MiB |
| 365 天 | 51.42 ms | 30.27 ms | 38.53 → 35.24 MiB |

四次运行均成功、`quick_check` 均为 `ok`，同一范围的新旧 JSON SHA256 完全相同。一次测试只能说明这组数据在该环境中的数量级，不能据此宣称一年查询有稳定的百分比加速，也不能推断冷缓存、磁盘繁忙或多用户访问时的尾延迟。该测试未查询实际历史库；结束后合成库全文件 SHA256 未变，临时目录已清理。

### 并发写入与启动维护

本机使用独立合成副本，同时运行四个 90 天读任务、各查询两次，并进行 12 次加速采样提交。流式实现的读请求 p50 为 7.34 秒、p95 为 8.40 秒，进程峰值 RSS 约 113.86 MiB；基线分别为 9.34 秒、12.40 秒、1,069.08 MiB。多个重查询同时执行仍有明显 CPU 和调度竞争，降低单次内存不等于消除并发开销。

两版的 12 次写入均完整持久化，未报丢桶，数据库检查通过；流式实现的单次采样加提交最大耗时为 13.53 毫秒。测试每 0.25 秒尝试一次并立即提交，比正常写入节奏更密集。它验证了这一压力样本下的读写并存，不是所有硬件和故障情况的数据安全保证。

同一数据规模下，已有日统计的正常启动约 4.56 毫秒，例行清理约 0.93 毫秒。删除日统计和游标以模拟旧分钟库后，首次补齐 90 天统计约 1.36 秒；再次启动约 1.66 毫秒，观测数与查询结果不重复。另以本地 FastAPI 客户端观察回填过程，29 批实时和健康请求均返回 200，实时请求最大约 40 毫秒；历史在初始化时返回 503，约 1.51 秒后可用。

这些测试覆盖聚合口径、查询工作集、一次回填和有限并发，不代替一年连续运行验收。原始数据本身是否连续，应以实际记录时间和质量标记判断。数据库不可写时，待写队列有 4,096 桶上限，超出会报告丢桶；同一数据库仍须使用一个后端 worker。备份与恢复应遵循[在线备份和维护说明](architecture.md#备份与维护)，同时保留校准配置。
