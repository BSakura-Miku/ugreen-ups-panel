# 发布与交付

当前流程：Docker Hub 提供面板镜像，GitHub 仓库提供 Compose、配置示例与宿主机采集器脚本。首次安装克隆仓库，安装采集器后通过 Compose 拉取并启动面板；日常面板更新通过镜像标签完成。详细步骤见 [README](../README.md)，维护者发布步骤见[贡献指南](../CONTRIBUTING.md#发布流程)。

后续 GitHub Release 只记录版本说明与镜像信息，不再额外制作源码包或部署包。0.3.1 已发布的附件保留供历史版本使用，不作为后续安装流程的依赖。

## 0.3.1 历史发布记录

本版将默认安装方式改为预构建面板镜像与轻量部署包。NAS 保留独立宿主机采集器，页面容器从快照读数据。功率模型、指标测点和默认关闭单机系数的行为不变。

### 发布内容

- Linux 被动 usbmon 采集器、systemd 安装/回退脚本。
- Docker Hub 面板镜像，以及包含 Compose、配置示例和采集器安装文件的轻量部署包。
- Docker 页面、只读 API、SQLite 聚合历史与 CSV。
- 供电状态、电量、电芯、电压、电池侧候选数据及硬件档案。
- 显式选择的 `local-19v-v1` 经验模型，默认配置 `none`。
- 协议、校准、架构、部署、安全及贡献文档。

本项目不附带 NAS 配置、账号凭据、实际部署数据库、专项采集记录或第三方拆解原图。公开资料引用原始来源链接。

### 升级说明

0.3.1 默认 Compose 不再现场构建，历史存储由命名卷改为部署目录中的 `./data` 绑定目录。旧数据不会因更换 Compose 文件自动出现在新目录中；需要先确认旧容器的 `/data` 实际挂载位置，停止面板写入，再使用迁移工具生成新目录中的数据库。原卷和原数据库保留，迁移验证完成前不要删除旧部署。

同一升级过程中，无需停止 NAS 的原 UPS 保护服务，也无需为了面板镜像更新重启宿主机采集器。只有采集器代码或服务配置变化时才重新运行其安装脚本。首次安装先创建可供容器 UID/GID `10001:10001` 写入的数据目录。

历史数据库自 0.3.0 起使用 schema 2，0.3.1 保持该结构，保存模型/质量身份以避免不同计算条件混合。升级前使用 README 中的 SQLite 备份接口生成一致备份，保留旧镜像、Compose 与宿主机配置。

已有采集器配置在不带参数的升级中保留。首次安装使用 `none`；需要已有单机模型时显式指定 `--calibration-profile local-19v-v1`。更改模式只影响之后的数据，不会重新标定旧历史。

如果回退到只支持 schema 1 的旧版，**需要停止面板并恢复升级前的数据库备份**，不能直接让旧程序写入已升级的数据库。恢复步骤见 [README](../README.md#历史与备份)。

完整能力与边界见[验证范围](validation.md)，功率公式见[校准说明](calibration.md)。

### 功能取舍与后续方向

本版保持只读监控，交流输入与电池放电使用固定、独立的展示位置；实时电流和功率的测点及精度边界保留在数据说明中。原始字段放在高级诊断，常用状态、曲线、电芯和事件留在概览。硬件档案补充资料来源，不把芯片规格当成本机探测结果。

暂不加入 UPS 控制、自动关机、插座联动、自动断电实验，以及没有独立依据的 SOH、负载率和剩余续航。这样可以保留与 NAS 原保护服务的清晰边界，也避免向用户提供没有验证基础的指标。

后续优先级：

1. 收集不同 NAS、NUT 版本和 US3000 批次的脱敏样本，建立兼容性矩阵。
2. 使用同测点的独立参考测量验证电流及功率，扩展校准范围和模型管理。
3. 按需增加只读 Prometheus 指标导出，继续沿用模型、质量与数据新鲜度标记。

### 发布验证

以下记录对应 0.3.1 发布时的测试集与部署方式：双架构镜像检查、公开镜像发布、x86_64 NAS 实际升级与历史迁移均已完成。当前主分支的测试集以 CI 为准。

| 检查项 | 结果 |
| --- | --- |
| `linux/amd64` 镜像 | 容器内实际架构为 `x86_64`，启动与接口检查通过 |
| `linux/arm64` 镜像 | 容器内实际架构为 `aarch64`，启动与接口检查通过 |
| 容器限制 | UID `10001`、只读根文件系统、移除全部 capabilities、禁用容器网络的隔离测试通过 |
| 静态资源 | 6 个前端资源可读取 |
| 数据库与导出 | SQLite 写入 3 条记录；测试范围内历史查询和 CSV 各返回预期的 2 条记录 |
| 模型与新鲜度 | `none` 配置不产生经验模型数值；过期快照正确标记不可用 |
| 自动化测试 | 全套 89 项通过，涵盖协议、模型、存储、API、安装、迁移及部署包完整性 |
| 前端 | TypeScript 与生产构建通过；npm 审计未报告已知漏洞 |
| Docker Hub | 公开仓库经匿名 API 确认，`0.3.1` 与 `latest` 均已发布 `amd64`、`arm64` 多架构镜像 |
| NAS 镜像部署 | 通过实际 `docker compose pull` 拉取并升级至 0.3.1，容器健康检查通过 |
| 历史迁移 | schema 2 历史、事件与元数据保留，数据库完整性检查通过，升级后历史继续增长 |
| 现场数据 | 实时采集新鲜、无存储错误、未报告待写桶丢弃；历史查询与 CSV 导出记录对应 |
| 原服务共存 | 面板升级期间宿主机采集器与原 NUT 保护服务持续运行，进程未重启 |

依赖审计反映检查当时数据库中的已知问题，不是永久安全保证。隔离测试证明面板镜像运行不依赖外部网络，首次下载部署包或拉取镜像仍需要相应网络访问。

真实 UPS 采集与现场升级的验证范围仍为 x86_64 NAS。`arm64` 已通过面板容器的软件运行检查，不代表 ARM NAS 的内核、usbmon 和原 UPS 驱动组合已经通过实机验证。
